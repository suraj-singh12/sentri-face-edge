## Cross-discipline conclusions

- **Product/interaction:** optimize repeated decision and navigation effort while keeping accepted-vs-proposed, incomplete-vs-complete, attendance-vs-mention and source-vs-derived status explicit. Absence of a screenshot is an audit gap, not evidence a feature should be removed.
- **Visual/accessibility:** the existing Mantine provider, semantic surface tokens, component families and breakpoints can support a coherent refinement. Rendered contrast, focus, clipping, long text and native input behavior still need independent observation.
- **Frontend/platform:** current controller ownership and stale-generation guards are assets. Resumable browser state and server draft state need to be distinguished in the evidence library; source running on macOS does not qualify the packaged Windows boundary.
- **Domain/security:** retain one identity graph, explicit finalization, independent evidence types, append-only corrections/history, canonical/lifecycle interpretation, target-bound Attach and Reference Only source authority. A design should not redefine these rules by reducing visible terminology.
- **QA/red team:** challenge any claim of exhaustive coverage derived only from JSX extraction, any synthetic result described as genuine inference, any loading capture called success, and any private diagnostic screenshot promoted to public evidence without inspection.

## Follow-up: J10 Sighting thumbnail and Person Graph keyboard parity

### SR-11 — Generic occurrence thumbnail appears inside a Person-specific Sighting card

**Observed evidence inspected:** `UX-06_J10_Step-01_Sightings-tab.png` shows Synthetic Beta's profile photo as SYNTHETIC 4 but its sole Sighting card thumbnail as SYNTHETIC 3. `UX-06_J10_Step-02_Sighting-photo-detail.png` opens Photos and shows SYNTHETIC 4. These are safe synthetic fixtures, not real faces.

**Source explanation:** [Sighting](../../src/sentriface/models.py) lines 378–392 is one canonical Person's presence in a finalized observation and contains a tuple of `ObservationMedia`; it does not own a face or embedding. [The store](../../src/sentriface/storage/sqlite_store.py) `_list_person_sightings`, line 15020, supplies **all observation media**. [API `_sighting_record`](../../src/sentriface/api_server.py), line 5005, selects the first nonempty media path as `image_path`. [PeopleView](../../frontend/src/views/PeopleView.jsx) `SightingImage`, lines 2238–2242, prefers that `detail.image_path` over Person gallery fallback. Therefore the card may depict another media item from the same Encounter without proving that the selected Person appears in that item. The [domain model](../../docs/DOMAIN_MODEL.md) P9 description explicitly states that Sighting does not own a face/embedding and retains occurrence media membership.

**Classification:** confirmed visual/navigation ambiguity; **not a demonstrated wrong participant assignment, wrong biometric ownership or backend contract violation**. The card does not explain that its thumbnail is generic Encounter media. `selectSightingPhoto`, PeopleView lines 1175–1183, tries to match an embedding ID or the generic image path against Person gallery records. A Sighting DTO lacks `embedding_id`; if the generic path has no Person gallery record, the current image remains selected while Photos opens. With several gallery records this may be a different selection than the card implies. The two observed frames establish inconsistency, while broader multiple-gallery selection behavior remains untested.

**Recommended direction / reuse / tradeoff:** label an occurrence thumbnail as such and provide an explicit Event detail route, or evaluate Person-specific `person_media` from the existing Encounter reads (`_encounter_person_media`) for the intended photo action. Preserve Sightings as presence, not face ownership: a legitimately present Person can lack a face/photo. Generic occurrence context can be useful, so replacing it without a fallback would lose information. No new thumbnail policy is approved by this audit.

### SR-12 — Person Graph edge inspection lacks the keyboard pattern already present in Explore

**Source evidence:** [PersonGraphView](../../frontend/src/views/PersonGraphView.jsx) lines 213–222 renders `.person-graph-edge-hit` as an SVG `line` with pointer enter/leave and `onClick` only: no `role`, `tabIndex`, accessible relationship name or keyboard activation. Lines 253–273 render nodes as actual buttons, but hovering a connected node sets an edge inspector (259–264) while keyboard activation selects a node and may navigate (266–268); no equivalent `onFocus` supplies the edge summary. The inspector instructs “Hover over a person or relationship. Select an edge to keep its evidence summary here” (lines 317–320).

**Existing reuse opportunity:** [WorldExploreCanvas](../../frontend/src/views/WorldExploreCanvas.jsx) line 48 already renders edges with `role="button"`, `tabIndex={0}`, accessible strength label, Enter/Space activation and `preventDefault`. It is a reusable interaction pattern, not permission to duplicate graph authority or change the graph model.

**Classification:** source-confirmed missing edge keyboard handlers/focusability; runtime keyboard traversal/assistive-technology consequence must be recorded before calling an executed accessibility failure. This does not mean all Person Graph controls are inaccessible: toolbar and node buttons already have keyboard semantics.

**Reasonable confirmation case:** open an edge-populated Person Graph in the actual runtime, begin from Back/toolbar, traverse Tab/Shift+Tab through a complete cycle without pointer hover and record active element/accessible names. Attempt to reach and Enter/Space-inspect the relationship summary; compare with clicking the edge and with Explore's keyboard edge action. Verify whether any existing alternative exposes the same evidence summary rather than merely related aggregate information. No injected `tabIndex`, forced focus on nonfocusable elements, DOM edits or fake screenshot state may be used to claim successful keyboard access.
